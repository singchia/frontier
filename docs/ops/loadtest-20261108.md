# Frontier 并发 benchmark（2026-11-08）

## 环境与口径

- 修复分支 `fix/edge-route-recovery-115`，业务代码基于 b2194c5；新增 benchmark 为本轮工作。
- Apple M4，10 个逻辑 CPU，16 GiB RAM，darwin/arm64，Go 1.24.13；固定 `GOMAXPROCS=4`。
- 单进程启动真实 Frontier servicebound/edgebound/exchange、一个 Service SDK 和一个 Edge SDK，通过 loopback TCP 通信。CPU、分配量与内存包含客户端、Frontier、Edge 和测试工具，不是 Frontier 单独的消耗。
- 路径为 Service SDK → Frontier → Edge SDK 回显；不经过 TUN、MASQUE、Docker、HTTP 或外部应用。使用 NewService，未涉及 Frontlas 查询与集群缓存。
- 每次请求 256 字节，校验等长回显。RPC、复用流、每次新建流分别测试 1/16/64/256 个固定 worker。worker 数独立于 GOMAXPROCS。
- 新建流是共享 TCP 连接内的 Geminio 流，不是每次建立 TCP 连接；包含新版就绪 RPC、回显和本地 AbortStream 调用，不等待远端全部清理完成。
- Go benchmark `-benchtime=3s -count=3`，3 秒为校准目标，不保证最终每个样本恰好 3 秒；表中为三轮中位数。非 race 模式测性能。
- 延迟为完整操作耗时，RPC 包含调用/校验，复用流包含写入/读取/校验，新流包含建流/回显/本地终止调用。所有测量操作均成功，故无失败延迟被排除。
- setup、预检、延迟排序不计入计时；每个操作仍包含计时与校验成本。

## 资源与观察

- 整个阶梯命令墙钟 162.65 秒，user CPU 315.14 秒、system CPU 142.15 秒，平均约 2.81 个 CPU 核；该值包含构建/校准/清理。
- 最大 RSS 416,301,056 字节，约 397 MiB（整个 benchmark 进程的峰值）。
- 新建流每次累计分配约 300 KB；这不是每条存活流常驻 300 KB。复用流每次约 14 KB，RPC 每次约 29 KB。
- 64→256 并发时吞吐未相应增长，复用流和新建流吞吐下降，P99 明显上升。不能仅凭这些结果确定瓶颈在 Frontier、SDK、GC 或调度；需要分进程采样/profile。
- 未做修改前后的同条件统计对比，不能据此量化 #116 新增就绪 RPC 的性能回归；也不是最大容量或长时间稳定性证明。

## 复现

```sh
GOMAXPROCS=4 make bench-concurrent

```

原始日志位于测试机 `/private/tmp/frontier-concurrent-results.log`、`/private/tmp/frontier-concurrent-resources.log`。

## 持续复测与失败边界

- 64 并发复用流，30 秒目标：最终 2,756,079 次回显，78,405 次/秒，P95 1.362 ms、P99 2.309 ms，零失败。
- 随后的 64 并发新建流，30 秒目标：426,628 次操作中 89,578 次失败（约 21.0%），首个样本为 `frontier stream setup: edge not online`。Go benchmark 失败后未输出完整速率/分位指标，因此不补算或猜测成功 QPS。
- 增加错误分类、首次失败时间与 Edge ID 记录，单独复测新建流：395,703 次操作，约 34.9 秒，11,352 次/秒，P99 11.39 ms，零失败。一次复测通过不能否定上一轮失败，短时 11k 流/秒不能当作已经验证的稳定容量。
- 进一步单独运行 60 秒目标：828,213 次新建流操作，实际约 71.2 秒，11,634 次/秒，P95 8.201 ms、P99 11.19 ms，零失败。当前是一次失败、随后两次单独复测通过，不能宣称故障稳定复现或已解决。

持续测试原始日志：`/private/tmp/frontier-concurrent-sustained.log`、`/private/tmp/frontier-concurrent-open-recheck.log`、`/private/tmp/frontier-concurrent-open-60s.log`。这些现象不能直接归因于迁移缓存修复，也未证明发生全连接死锁；需要定位 Edge 为什么离开本机在线表。

工具检查：所有模式/并发档以 `GOFLAGS=-race`、`-benchtime=256x` 做了小样本并发检查，全部通过；该组不用于性能数字。`go vet ./test/bench` 和 `git diff --check` 通过。


## reset 背压修复后的高并发长测

修复为 Geminio 本地分支 `fix/reset-backpressure`，提交 `46e45fd`，基于 main `5b8b07f`。通过独立 modfile 替换依赖，不修改正式部署。工具链 Go 1.25.0，Apple M4，GOMAXPROCS=4。

新增 benchmark 参数：`FRONTIER_BENCH_CONCURRENCY=512,1024` 可以指定并发档；`FRONTIER_BENCH_MONITOR=1` 每 15 秒报告完成数、失败数、实际 Edge/Service 拨号次数、goroutine 和 Go 堆内存。拨号计数包含失败的拨号尝试。采样覆盖整个 Service+Frontier+Edge 进程，不能视为单独 Frontier 的资源占用。

长测依然每次新建 Geminio 流，校验 256 字节 echo 后 Abort；不是 HTTP QPS，不包含 TUN/MASQUE，也不是每次新建 TCP 连接。监控模式过滤预期 `stream forward raw ... stream aborted` 日志以避免大量文件写入，保留其他诊断日志；因此不将新结果与此前未过滤日志的短测做直接性能对比。

每档用独立进程、`BENCH_CONCURRENT_COUNT=1`。Go 会先校准操作数，每次校准创建自己的 fixture；最终计量阶段使用同一 fixture。300s 是 Go 目标计量时间，实际耗时随校准估计有所偏差，不能把校准之间的新连接当作重连。最终统计仅使用最后一个计量样本。

```sh
FRONTIER_BENCH_CONCURRENCY=512 FRONTIER_BENCH_MONITOR=1 FRONTIER_BENCH_DIAGNOSTICS=1 GOMAXPROCS=4 make bench-concurrent BENCH_CONCURRENT_PATTERN=BenchmarkFrontierConcurrent/open BENCH_CONCURRENT_TIME=300s BENCH_CONCURRENT_COUNT=1
```

使用本地修复时另外设置 GOTOOLCHAIN=go1.25.0 和指向独立 modfile 的 GOFLAGS。大并发启动前，512/1024 各 2048 次操作的 race 冒烟检查通过。

### 高并发长测结果

| 并发 | 最终计量时间 | 请求数 | 成功/秒 | P50 | P95 | P99 | 失败 | Edge/Service 拨号次数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 512 | 346.531s | 3,744,212 | 10,805 | 46.44ms | 65.17ms | 79.25ms | 0 | 1 / 1 |
| 1024 | 354.304s | 3,556,683 | 10,039 | 102.0ms | 137.9ms | 158.9ms | 0 | 1 / 1 |

两档最终计量共 7,300,895 次请求、700.835 秒（约 11 分 41 秒），不含校准；含校准、构建和清理的两条命令墙钟合计 906.83 秒。每档的初始和最终 Edge ID 一致，所有 15 秒采样和最终统计中 Edge/Service 拨号次数均为 1，没有靠重连恢复。两档测量结束 goroutine 均为 55。

- 512 并发：15 秒采样 Go 堆 145.7–281.5 MiB；命令报告峰值 RSS 398.1 MiB。
- 1024 并发：15 秒采样 Go 堆 221.5–507.6 MiB；命令报告峰值 RSS 647.0 MiB。

资源覆盖客户端 SDK、Frontier 和 Edge 同进程，命令峰值 RSS 还受构建子进程影响，不能作为单个 Frontier 的内存规格。采样堆内存随 GC 波动，未观察到持续单向增长，但这不是泄漏不存在的证明。

并发翻倍后吞吐未增长，P99 约翻倍；本机固定 GOMAXPROCS=4 下已呈吞吐平台，不能据此推断生产分布式集群的最大容量。实验未再复现 reset 积压导致 Edge 整连接离线。日志仍有校准 fixture 清理后的 database closed，以及少量迟到包找不到 dialogue 的记录，未计为业务请求失败；这些已知清理/迟到包日志需与计量期间的离线故障区分。

原始日志：`/private/tmp/frontier-reset-c512-5m.log`、`/private/tmp/frontier-reset-c1024-5m.log`；结构化结果与采样：`/private/tmp/frontier-reset-soak-results.json`。修复依然是本地分支，未发布或部署。
